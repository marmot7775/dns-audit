# Doc 102: thread cap on the droplet makes every audit fail

(Sent as "Doc 101"; renumbered because Doc 101 is the result-card areas.)

## Symptom

2026-10-15 04:29 UTC. Every fresh audit returned `server_error` in
under a second. errors.log: `RuntimeError: can't start new thread`,
raised from `_shared_executor.submit` inside `run_full_audit`.
`systemctl show dns-auditor` reported TasksCurrent 1107 and TasksMax
1107. A restart cleared it. The same error is in errors.log on
2026-09-21 for thecarraways.co.

## Cause

`audit_engine.py` builds three pools sized off
`MAX_CONCURRENT_AUDITS` (8): `_shared_executor` 72,
`_probe_executor` 352, `_dkim_executor` 688, 1112 workers in total.
ThreadPoolExecutor never retires an idle worker, and a submit
creates a new thread whenever no worker is idle, so each DKIM wave
of 86 selectors can add 86 threads. Two audits after the restart
took the process from 6 threads to 105. The unit file sets no
TasksMax, so systemd uses its default, 15 percent of kernel
threads-max, 1107 on this droplet. That is below the pools'
combined ceiling, so with enough overlapping traffic the process
reaches the cap and every audit fails until someone restarts it.

## Fix, in this order

1. **Unit file.** In `deploy/dns-auditor.service` add
   `TasksMax=4096` under `[Service]`. The comment says TasksMax
   must exceed `AUDIT_THREAD_CEILING` in `audit_engine.py` plus
   about 100 for uvicorn, anyio, the per audit stream thread in
   `server.py`, and sentry, and that `server.py` logs a warning at
   startup when it does not. Put no fixed thread count in the
   comment; step 4 changes it. Apply the same line to the live
   unit on the droplet, `daemon-reload`, restart, and confirm with
   `systemctl show dns-auditor -p TasksMax`.

2. **Ceiling constant and startup check.** In `audit_engine.py`
   add a module constant `AUDIT_THREAD_CEILING` equal to the sum of
   the three pools' `max_workers`, with a comment saying the unit's
   TasksMax must exceed it plus uvicorn, anyio and sentry overhead.
   In `server.py`, after the audit nameserver log line, read
   `/sys/fs/cgroup/system.slice/dns-auditor.service/pids.max` when
   it exists. If it is a number and below
   `AUDIT_THREAD_CEILING + 100`, log a WARNING naming both numbers.
   Do not fail startup on it.

3. **Health endpoint.** Add `threads`, the value of
   `threading.active_count()`, and `thread_ceiling`,
   `AUDIT_THREAD_CEILING`, to `/api/health`. Leave `status` alone.
   Update the no-leak health test so the new fields are allowed.

4. **Smaller DKIM pool.** 688 workers exists for 8 concurrent
   audits each submitting a full 86 selector wave at the same
   instant. In `spf_intelligence.py` add `DKIM_WAVE_CHUNK`, equal
   to `DKIM_FALLBACK_CHUNK` (52), and have `smart_dkim_check`
   submit the priority wave in chunks of `DKIM_WAVE_CHUNK` through
   the existing `_run_wave` path, the same way the generic fallback
   already runs. Between chunks, stop once `len(found)` reaches
   `DKIM_MAX_FOUND`, matching the break inside a wave. Size
   `_dkim_executor` at
   `max(20, MAX_CONCURRENT_AUDITS * DKIM_WAVE_CHUNK)`, which is 416,
   and replace the 86 x 8 comment above it with that arithmetic. Do
   not size the pool below `DKIM_FALLBACK_CHUNK` per audit, or
   concurrent fallback waves queue.

   Measure google.com, microsoft.com and proton.me three times each
   before and three times after. The DKIM selectors found must be
   identical on every run, and the median elapsed time must be
   within 2 seconds of before. If the chunking changes results,
   stop and report instead of forcing it.

5. **Tests.**
   1. `AUDIT_THREAD_CEILING` equals the sum of the three pools'
      `_max_workers`.
   2. `_dkim_executor._max_workers` is at least
      `MAX_CONCURRENT_AUDITS * DKIM_FALLBACK_CHUNK`.
   3. The health endpoint returns `threads` and `thread_ceiling`.

   Run the full suite and report the count before and after.

## Report back

1. TasksCurrent from `systemctl show dns-auditor -p TasksCurrent`
   after ten audits, before and after the fix.
2. `AUDIT_THREAD_CEILING` before and after.
3. Suite counts before and after.
4. The three median timings before and after.
5. Anything in step 4 that did not hold.
